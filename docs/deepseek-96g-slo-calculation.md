# 10T DeepSeek 在 96 GB / 486 T、128 卡上的计算过程

本文对应 `docs/deepseek-96g-slo.pptx` 的 14 页。数字来自生成该文件的计时模型，并与幻灯片、备注中的边界值对齐。另有两份场景稿，不替换本档 25% 口径，见第 18 节。

公式全部写在 Markdown 代码块里，不用 LaTeX。代码块中 `#` 后面是符号注释。容量按十进制：`1 GB = 10^9 字节`，`1 TB = 10^12 字节`。幻灯片上的「秒 / 毫秒」是四舍五入后的展示值，正文同时给出未舍入的代入结果。

集合通信按 Hockney 计算：每一层的 AllReduce、dispatch、combine 各付 5 微秒启动，再加字节/带宽。5 微秒是这套 8 卡 fullmesh 与 128 卡 D2D 上的规划值，不是实测。调度、kernel 启动、RMSNorm、RoPE、Router、残差、logits、sampling 和 P/D 控制面没有实测值，不并进 10 秒或 10/30 毫秒。KV 换入仍整段计入 TPOT。Prefill 的拉 prefix、融合 kernel、AllReduce 串行相加，只在融合 kernel 内部对 HBM 和 FLOP 取最大。

下文第 8 节以后的代入表仍是未加启动项、按 98% 命中写出的旧数。当前幻灯片以 `docs/build_deepseek_96g_slo_ppt.py` 为准。

## 1. 这份 PPT 回答什么

同一份 128 卡副本上，10T DeepSeek 外推能否同时满足：

| 目标 | 冷请求最大输入 | 98% 命中时 4K 的 Prefill 全局批 | 4K 的 Decode 全局批 |
| --- | ---: | ---: | ---: |
| TTFT ≤ 10 秒，TPOT ≤ 10 毫秒 | 373,358 token | 54,928 | 223 |
| TTFT ≤ 10 秒，TPOT ≤ 30 毫秒 | 373,358 token | 54,928 | 10,496 |

两条目标的 TTFT 相同，差别只在 Decode 批量。30 毫秒从 256K 输入开始把 KV 换进 DDR 池，换入走 H2D。

边界复核：

```
冷请求 S = 373358 时 TTFT = 10.000000 秒
S = 373359 时 TTFT = 10.000010 秒     # 第一条超出 10 秒

98% 命中、4K、BS = 54928 时 TTFT = 9.998575 秒
BS = 54929 时 TTFT = 10.000028 秒

4K、BS = 223 时 TPOT = 9.983791 毫秒
BS = 224 时 TPOT = 10.002469 毫秒

4K、BS = 10496 时 TPOT = 29.801219 毫秒
BS = 10497 时 TPOT = 30.046506 毫秒
```

本次相对上一版只改了两处计时输入。张量算力加上 108 T FP8 core、效率 0.6，有效峰值从 340.2 T 变成 405.0 T。MoE dispatch 按 FP8、1 字节，combine 按 BF16、2 字节，两段时间不再相等。Decode 仍是单请求串行相加，不把 AllReduce 或 dispatch 盖进 kernel。KV 字节公式不动。

`BS` 是 128 卡上的全局请求数，不是单卡请求数。

## 2. 符号

| 符号 | 含义 | 本档取值 |
| --- | --- | --- |
| `N` | 一份副本的 GPU 数，也是 MoE 的 EP 规模 | 128 |
| `TP` | Attention 张量并行，限制在一台机器的 8 卡 fullmesh 内 | 8 |
| `DP` | Attention 数据并行组数，`DP = N / TP` | 16 |
| `NODE` | 一台机器的 GPU 数 | 8 |
| `n` | 最忙 TP 组里的请求数，`n = ceil(BS / DP)` | 随 BS 变化 |
| `L` | Transformer 层数 | 61 |
| `H` | 隐藏维 | 7168 |
| `DFF` | 专家中间维 | 3072 |
| `E` | 路由专家总数 | 2469 |
| `TOPK` | 每个 token 每层选择的路由专家数 | 6 |
| `N_CSA` | Compressed Sparse Attention 层数 | 30 |
| `N_HCA` | Head-Compressed Attention 层数 | 31 |
| `S` | 一条请求的输入长度，单位 token | 场景变量 |
| `P` | 命中的 prefix 长度 | 冷请求为 0；98% 命中时为 `0.98 S` |
| `Q` | 需要现算的 token 数。单请求记 `q`，全局记 `BS * q` | 冷请求 `q = S`；98% 命中 `q = 0.02 S` |
| `b_KV` | 每增加 1 个历史 token，61 层新增的 KV 字节。代码名 `BPT` | 4939.5 字节/token |
| `K_window` | 每层最近 128 token 的完整滑窗，不随更长历史再增长。代码名 `FIXED` | 4,497,408 字节 |
| `K(S)` | 一条请求的完整 KV 存量。代码名 `store_seq(S)` | `b_KV * S + K_window` |
| `R_KV(S)` | Decode 一步真正读的 KV 字节，按一条请求、全部层。代码名 `n_csa_read(S)` | 见第 5.2 节 |
| `W_ONE` | 一个专家在 61 层上的参数个数；共享专家按 FP8，字节数等于这个数 | 4,029,677,568 |
| `ATTN` | Attention 权重参数量，按 FP8 计也是字节数 | 19.35 × 10^9 |
| `PROJ` | 每个 token 的 Attention 投影 FLOP | `2 * ATTN = 3.87 × 10^10` |
| `PEAK` | 单卡有效张量算力。486 T×0.70 加 108 T×0.60 | 405.0 × 10^12 FLOP/s |
| `HBM_BW` | 单卡有效 HBM 带宽 | 3.20 × 10^12 字节/s |
| `D2D` | 单卡有效 D2D 带宽，承载 MoE 的 dispatch / combine | 320 × 10^9 字节/s |
| `P2P` | 单卡 fullmesh 聚合后的有效 AllReduce 带宽 | 280 × 10^9 字节/s |
| `PARAM` | 单卡 P→D 带宽，参数面物理带宽的 80% | 40 × 10^9 字节/s |
| `PREFIX_PULL` | 单卡拉 prefix 带宽，参数面物理带宽的 25% | 12.5 × 10^9 字节/s |
| `H2D` | 单卡有效 Host-to-Device 带宽 | 51.2 × 10^9 字节/s |
| `POOL` | Decode 从 DDR 池换入 HBM 的有效带宽。本档等于 `H2D` | 51.2 × 10^9 字节/s |
| `ROOM` | 128 卡合计可放 KV 的 HBM 字节 | 5.719964 × 10^12 |
| `f` | KV 存量溢出到 DDR 池的比例。代码名 `spill` | 0 到 1 |
| `align(m)` | 16 行对齐效率，`m / (ceil(m / 16) * 16)` | 0 到 1 |
| `e_hot` | 最忙 EP 卡上估计会醒的路由专家数 | 0 到 19.289 |
| `hot_assign` | 最忙 EP 卡收到的 token 指派次数，已含 61 层之前的按层模型，见第 7.3 节 | 随 token 数变化 |

`ceil(x)` 表示向上取整。`max(a, b)` 表示取较大者。`exp` 是自然指数。

## 3. 硬件有效带宽

标称值和效率先折成计时用的字节每秒。比特到字节一律除以 8。

### 3.1 算力和 HBM

```
PEAK_BASE  = 486 × 10^12 × 0.70
           = 340.2 × 10^12 FLOP/s

PEAK_EXTRA = 108 × 10^12 × 0.60
           = 64.8 × 10^12 FLOP/s     # 增量 FP8 张量 core

PEAK       = 340.2 × 10^12 + 64.8 × 10^12
           = 405.0 × 10^12 FLOP/s

HBM_BW = 4 × 10^12 × 0.80
       = 3.20 × 10^12 字节/s

HBM 容量 = 96 × 10^9 字节/卡
```

`0.70` 是原张量算力的效率，`0.60` 是增量 core 的效率。`0.80` 是访存和通信效率。Indexer、HCA 打分、稀疏注意力、投影和专家 GEMM 都除以这个 `PEAK`。非张量效率按 0.70 备着，TopK、RMSNorm、RoPE 没有单独的 FLOP 项，不进入秒数。

### 3.2 D2D、fullmesh、参数面、H2D

```
D2D 峰值 = 3.2 × 10^12 bit/s / 8
         = 400 × 10^9 字节/s

D2D      = 400 × 10^9 × 0.80
         = 320 × 10^9 字节/s          # MoE dispatch 和 combine

单条 fullmesh 链路 = 400 × 10^9 bit/s / 8
                    = 50 × 10^9 字节/s

7 条链路聚合峰值 = 7 × 50 × 10^9
                = 350 × 10^9 字节/s   # 低于 D2D 口 400 × 10^9，不受 D2D 口再截断

P2P = 350 × 10^9 × 0.80
    = 280 × 10^9 字节/s               # TP AllReduce

参数面峰值 = 400 × 10^9 bit/s / 8
          = 50 × 10^9 字节/s

PARAM = 50 × 10^9 × 0.80
      = 40 × 10^9 字节/s              # P→D。不是 fullmesh

PREFIX_PULL = 50 × 10^9 × 0.25
            = 12.5 × 10^9 字节/s      # prefix 拉取。存储服务整个 Prefill 集群，按物理带宽的 25%，不叠乘 80%

H2D = 64 × 10^9 × 0.80
    = 51.2 × 10^9 字节/s
```

每条 fullmesh 链路是 400 Gb/s，不是每卡聚合 400 Gb/s。8 卡里每卡连另外 7 卡，所以 AllReduce 用 280 GB/s。参数面仍是每卡一条 400 Gb/s。P→D 取 80%，有效 40 GB/s。prefix 拉取取物理带宽的 25%，有效 12.5 GB/s，因为存储同时服务整个 Prefill 集群。Prefill 与 Decode 都是 TP=8、DP=16。

### 3.3 DDR5 与 Decode 换入

```
单机 DDR5 有效带宽 = 1288.8 × 10^9 × 0.80
                   = 1031.04 × 10^9 字节/s

每卡 DDR 份额 = 1031.04 × 10^9 / 8
             = 128.88 × 10^9 字节/s

每卡 DDR 容量份额 = 768 × 10^9 / 8
                 = 96 × 10^9 字节
```

DDR 池标称 480 GB/s，但本档要求 Decode 的外部访存进入 GPU 时走 H2D。三条路取最慢的一条：

```
POOL = min(480 × 10^9 × 0.80, 64 × 10^9 × 0.80, 128.88 × 10^9)
     = min(384 × 10^9, 51.2 × 10^9, 128.88 × 10^9)
     = 51.2 × 10^9 字节/s
```

HBM 里已经驻留的权重和 KV 仍按 3.20 TB/s 读。MoE 的 EP 仍走 320 GB/s 的 D2D。只有「DDR 池 → GPU HBM」这一段是 51.2 GB/s。

## 4. 10T 外推和每卡权重

### 4.1 单个专家的参数

一个路由专家有 gate、up、down 三个矩阵，每个矩阵是 `H × DFF`，61 层各有一份。

```
W_ONE = 3 × H × DFF × L
      = 3 × 7168 × 3072 × 61

7168 × 3072 = 22,020,096
3 × 22,020,096 = 66,060,288          # 单层
66,060,288 × 61 = 4,029,677,568      # 一个专家，61 层
```

1.6T 论文模型有 384 个路由专家：

```
384 × 4,029,677,568 = 1,547,396,186,112
```

论文总参数 `1.600 × 10^12` 减去路由专家，剩下共享专家、Attention、词表和其他项：

```
其余 = 1.600 × 10^12 − 1,547,396,186,112
     = 52,603,813,888
     ≈ 5.260 × 10^10
```

10T 只增加路由专家个数，不动 `L / H / DFF`：

```
E = (10^13 − 5.260 × 10^10) / 4,029,677,568
  = 9,947,396,186,112 / 4,029,677,568
  = 2469
```

回代：

```
总参数 = 2469 × 4,029,677,568 + 52,603,813,888
       = 9,947,396,186,112 + 52,603,813,888
       = 10,000,000,000,000
```

激活参数不变：每 token 仍是 6 个路由专家加 1 个共享专家，约 `4.9 × 10^10`。激活比从 `4.9e10 / 1.6e12 = 3.06%` 降到 `4.9e10 / 1e13 = 0.49%`。

### 4.2 FP4 专家表和每卡切分

路由专家按 FP4，每个参数 0.5 字节。共享专家按 FP8，每个参数 1 字节，所以字节数等于 `W_ONE`。

```
一个路由专家 = 4,029,677,568 × 0.5
             = 2,014,838,784 字节
             = 2.015 GB

FP4 专家表 = 2469 × 2,014,838,784
          = 4,974,636,957,696 字节
          = 4.975 TB

640 GB 卡下限 = ceil(4.975 × 10^12 / 640 × 10^9)
             = ceil(7.773)
             = 8 张
```

时延模型不用 640 GB 卡，而用 96 GB × 128 卡。路由专家按 EP 均分，共享专家每卡一份，Attention 按 TP 均分：

```
每卡路由专家个数 = 2469 / 128 = 19.2890625
每卡路由权重     = 4,974,636,957,696 / 128
                 = 38,864,351,232 字节
                 = 38.864 GB

每卡共享权重     = 4,029,677,568 字节
                 = 4.030 GB

每卡 Attention   = 19.35 × 10^9 / 8
                 = 2,418,750,000 字节
                 = 2.419 GB

每卡模型权重     = 38.864 + 4.030 + 2.419
                 = 45.313 GB
```

系统预留固定 6 GB。它覆盖 runtime、碎片和未单列的临时区，饼图里不把激活再拆出来。

```
每卡 KV 空间 = 96 − 45.313 − 6
            = 44.687 GB
            = 44,687,221,200 字节

128 卡 KV 空间 ROOM = 128 × 44,687,221,200
                    = 5,719,964,313,600 字节
                    = 5.720 TB
```

## 5. KV：存量、滑窗、一步读取量

### 5.1 每 token 增量 `b_KV`

CSA 不给每个原始 token 留一份完整 latent。每 4 个 token 留一份 576 字节压缩 latent，再加一份 64 字节索引。HCA 每 128 个 token 留一份 576 字节 latent。576 已经是 K/V 合并后的 latent，不再乘 2。

```
CSA 一层 = 576 / 4 + 64 / 4
         = 144 + 16
         = 160 字节/token

30 层 CSA = 30 × 160
          = 4,800 字节/token

HCA 一层 = 576 / 128
         = 4.5 字节/token

31 层 HCA = 31 × 4.5
          = 139.5 字节/token

b_KV = 4800 + 139.5
     = 4939.5 字节/token
```

CSA 占 `4800 / 4939.5 = 97.18%`。

### 5.2 固定滑窗和完整存量

每层另留最近 128 个 token 的完整 576 字节滑窗。输入不短于 128 时，这项不随 `S` 再涨。

```
K_window = 61 × 128 × 576
         = 4,497,408 字节
         = 4.497 MB

K(S) = b_KV × S + K_window
     = 4939.5 × S + 4,497,408
```

三个长度：

```
4K   = 4096
K    = 4939.5 × 4096 + 4,497,408
     = 20,232,192 + 4,497,408
     = 24,729,600 字节
     = 24.730 MB

256K = 262144
K    = 4939.5 × 262144 + 4,497,408
     = 1,294,860,288 + 4,497,408
     = 1,299,357,696 字节
     = 1.299 GB

1M   = 1048576
K    = 4939.5 × 1048576 + 4,497,408
     = 5,179,441,152 + 4,497,408
     = 5,183,938,560 字节
     = 5.184 GB
```

128 卡能放的请求条数是整副本容量除以单条存量，再向下取整：

```
cap(S) = floor(ROOM / K(S))

cap(4096)   = floor(5,719,964,313,600 / 24,729,600)   = 231,300
cap(262144) = floor(5,719,964,313,600 / 1,299,357,696) = 4,402
cap(1048576)= floor(5,719,964,313,600 / 5,183,938,560) = 1,103
```

这是「如果只受容量限制，128 卡一共能放多少条」。实际批量还要先被 TTFT 或 TPOT 卡住，所以摸高批远小于 `cap(S)`。

### 5.3 Decode 一步读取量 `R_KV(S)`

存量里的 CSA latent 不会每步全读。CSA 每步只读压缩索引，以及最多 1024 条被选中的完整 latent。HCA 按 128:1 的压缩历史读。滑窗全读。

```
sel = min(1024, S / 4)                 # CSA 本步选中的压缩 token 数

R_KV(S) = 30 × (S / 4) × 64            # CSA 索引，历史全读
        + 31 × (S / 128) × 576         # HCA 压缩 latent
        + 30 × sel × 576               # CSA 选中的完整 latent
        + 4,497,408                    # 61 层滑窗
```

4K 时 `S / 4 = 1024`，选择上限刚好等于全部压缩 token，所以读取量等于存量：

```
索引 = 30 × 1024 × 64        = 1,966,080
HCA  = 31 × 32 × 576         = 571,392
选中 = 30 × 1024 × 576       = 17,694,720
滑窗 = 4,497,408
R_KV(4096) = 24,729,600 字节 = K(4096)
```

256K 只选 1024 条，存量远大于读取量：

```
索引 = 30 × 65536 × 64       = 125,829,120
HCA  = 31 × 2048 × 576       = 36,569,088
选中 = 30 × 1024 × 576       = 17,694,720
滑窗 = 4,497,408
R_KV(262144) = 184,590,336 字节 = 184.6 MB

K(262144) = 1,299,357,696 字节
读取 / 存量 = 184.6 MB / 1.299 GB = 14.2%
```

容量判断用 `K(S)`。换入时间和 HBM 读时间用 `R_KV(S)`。溢出比例高时，换入时间仍可能短于 Attention 计算，就是因为没把整段存量搬进 HBM。

## 6. 并行切分

```
TP = 8
DP = 16
EP = 128

n = ceil(BS / 16)          # 最忙 TP 组的请求数。Prefill 与 Decode 相同
每卡条数 = BS / 128         # 展示用平均条数；KV 和 AR 不用这个平均数
```

一条请求不跨副本。加 Prefill 或 Decode 节点是多放几份 128 卡副本，单条 TTFT / TPOT 不变。

Attention 的 KV、AllReduce、投影都先落在这 `n` 条上，再除以 `TP = 8`。MoE 按 128 张卡做专家并行，时间取最忙卡，不取 128 卡平均。

## 7. 三个子过程

后面的 TTFT 和 TPOT 都调用这三节。先把公式定死，再代入场景。

### 7.1 TP AllReduce

8 卡 fullmesh 的通信量仍按 ring 的 `2 × (TP − 1) / TP` 计，带宽用 7 链路聚合后的 280 GB/s。每个 token 的 hidden 是 BF16，2 字节。61 层各做一次。

```
每层字节 = 2 × (8 − 1) / 8 × (行数 × 7168 × 2)
         = 1.75 × 行数 × 14,336

T_AR = 61 × (5 × 10^-6 + 每层字节 / 280 × 10^9)
```

Prefill 的「行数」是最忙 TP 组的现算 token 行 `n × q`。Decode 的「行数」是 `n`，因为一步只生成 1 个 token。

AR 不和 GEMM 重叠。Decode 把它加在 Attention kernel 后面。Prefill 先把 prefix 整段拉完，融合 kernel 内部只对 HBM 和计算取最大，AR 再加在 kernel 后面。

### 7.2 Attention FLOP

单请求、现算 `q` 个 token、前面已有 `p` 个 prefix token 时，query-context 对的数量是：

```
C = q × p + q × (q + 1) / 2
```

`q × p` 是新 token 看 prefix。`q × (q + 1) / 2` 是新 token 之间的因果三角。98% 命中且 `S` 很大时，`p = 0.98 S`、`q = 0.02 S`，平均每个新 token 看到约 `0.99 S`，也就是约 99% 的完整上下文。

四个 FLOP 项都是一条请求、全部层：

```
F_idx  = 30 × 4096 × C
F_hca  = 31 × 2048 × C
F_core = 30 × 262144 × (1024 + 128) × q
F_proj = 3.87 × 10^10 × q
```

注释：

- `4096`：CSA indexer 每个 query-context 对的 FLOP。冷请求 `p = 0` 时 `C ≈ S^2 / 2`，所以 `30 × 4096 × C ≈ 30 × 2048 × S^2`。幻灯片上的 `2048 × S^2` 是这个大 `S` 近似，计时用精确的 `C`。
- `2048`：HCA 每个 query-context 对的 FLOP。同样，`31 × 2048 × C ≈ 31 × 1024 × S^2`。
- `262144`：每个 query 对一个被选 KV token 的稀疏注意力 FLOP。选中上限 1024，再加 128 滑窗。
- `3.87 × 10^10`：每个 token 的投影 FLOP，等于 Attention 参数量乘 2，对应一次乘加。

最忙 TP 组有 `n` 条请求。16 行对齐效率为 `align(n × q)`。组内 FLOP 再除以 8 张卡：

```
T_compute = n × (F_idx + F_hca + F_core + F_proj) / (8 × PEAK × align(n × q))
```

四项分别除以同一个分母，得到幻灯片上的 indexer、HCA、稀疏注意力、投影。

Decode 一步只有 1 个新 token，上下文就是完整 `S`，不再做三角：

```
F_score = 30 × 4096 × S
        + 31 × 2048 × S
        + 30 × 262144 × (min(1024, S / 4) + 128)

T_compute = n × (F_score + PROJ) / (8 × PEAK × align(n))
```

`PEAK = 405.0 × 10^12`。第一项 `30 × 4096 × S` 是 CSA indexer，随输入线性增长；`S ≥ 4096` 后第三项不再增长，因为最多选 1024 条压缩 token。

### 7.3 MoE：最忙卡、16 行砖、三段相加

输入是全局 token 数 `T`。Prefill 传入 `BS × q`，Decode 传入 `BS`。

最忙卡的指派次数取「均值 + 2 倍标准差」，并且不超过全部指派：

```
mean = T × 6 / 128
var  = mean × (1 − 1 / 128)
hot  = min(T × 6, mean + 2 × sqrt(var))
```

有多少路由专家会醒，用一次投 6 个专家的覆盖率，再对每卡 `2469 / 128` 个专家做均值 + 2 倍标准差：

```
frac    = 1 − exp(−6 × T / 2469)
experts = 2469 / 128 = 19.2890625
std     = sqrt(experts × frac × (1 − frac))
e_hot   = min(experts, experts × frac + 2 × std)
```

每个醒着的专家拿到 `hot / e_hot` 个 token，单独向上对齐到 16 的倍数。共享专家吃本卡 token，至少 1 个，同样对齐：

```
tok          = hot / e_hot
routed_rows  = e_hot × ceil(tok / 16) × 16
shared_tokens = max(1, ceil(T / 128))
shared_rows   = ceil(shared_tokens / 16) × 16
ue            = tok / (ceil(tok / 16) × 16)     # 砖利用率
```

权重字节：醒着的路由专家按 FP4，共享专家整份 FP8。除以 HBM 带宽得到读权重时间。

```
权重字节 = e_hot × 2,014,838,784 + 4,029,677,568
T_weight = 权重字节 / 3.20 × 10^12
```

GEMM：每个 padding 后的行，在 61 层各做 3 个矩阵乘，每个矩阵乘按 `2 × H × DFF` FLOP 计，所以系数是 6。

```
F_gemm = (routed_rows + shared_rows) × 6 × 7168 × 3072 × 61
T_gemm = F_gemm / PEAK
```

EP 通信按最忙卡的 `hot` 次指派。dispatch 是 FP8，每元素 1 字节；combine 是 BF16，每元素 2 字节。两段都不能和 GEMM 重叠，彼此也不能重叠。带宽项里 combine 的字节是 dispatch 的 2 倍；每一层两边还各加 5 微秒，所以两段时间不再是 2 倍关系：

```
T_dispatch = 61 × (5 × 10^-6 + hot × 7168 × 1 / 320 × 10^9)
T_combine  = 61 × (5 × 10^-6 + hot × 7168 × 2 / 320 × 10^9)
```

融合 kernel 里读权重和 GEMM 取最大。kernel 前后各加一次 EP：

```
T_MoE = T_dispatch + max(T_weight, T_gemm) + T_combine
```

单 token、TopK=6、61 层的结构量与计时用的是同一套 1+2 字节：

```
单 token = 6 × (1 + 2) × 7168 × 61
         = 7,870,464 字节
```

计时不直接乘 `6 × token 数`，而是乘最忙卡的 `hot`。负载不均和 16 行 padding 都进秒数，结构展示式里没有这两项。

## 16. 固定开销为什么不加进摸高

幻灯片把下面几项列成未计入：

```
固定开销 = 调度
         + kernel 启动
         + RMSNorm / RoPE / Router / 激活 / 残差
         + logits / sampling
         + P/D 控制
```

没有实测值就不编一个毫秒数。因此：

- 10 秒、10 毫秒、30 毫秒都是数据面预算被算满后的上限。
- 生产上要先从这些预算里扣掉测得的固定开销，再重跑 `BS` 和最大 `S` 的搜索。
- Prefill 不再做跨 query chunk 流水。拉 prefix、融合 kernel、AllReduce 按顺序相加。

## 17. 计时规则一览

```
TTFT Attention = 拉 prefix + max(HBM, Attention 计算) + AR
TTFT MoE       = dispatch(FP8) + max(读专家权重, GEMM) + combine(BF16)
TTFT           = TTFT Attention + TTFT MoE + P→D 尾巴

TPOT Attention = SWAP + max(HBM, Attention 计算) + AR
TPOT MoE       = dispatch(FP8) + max(读专家权重, GEMM) + combine(BF16)
TPOT           = TPOT Attention + TPOT MoE
```

`AR`、`dispatch`、`combine` 都是 `61 × (5 微秒 + 该层字节 / 带宽)`。5 微秒加在对应集合通信上，不和 kernel 取最大。

允许取最大的只有融合 kernel 内部：

- Prefill 与 Decode 的 Attention kernel：HBM 读取和 FLOP。
- MoE 的专家 kernel：读权重和 GEMM。

必须相加的是：

- Prefill 的拉 prefix、Attention kernel、AR。prefix 整段先拉完，AR 不和 kernel 重叠。
- Attention 整段和 MoE 整段。
- dispatch 与 combine 两个方向。dispatch 每元素 1 字节，combine 每元素 2 字节，时间不相等。
- Decode 的 SWAP、Attention kernel、AR。SWAP 先把 KV 写进 HBM，kernel 再读 HBM，AR 不假设已经和投影融合。

KV 的分工：

- 容量和饼图用 `K(S) = 4939.5 × S + 4,497,408`，再按 `n / 8` 放到最忙卡。
- Decode 的 HBM 时间和 H2D 换入用 `R_KV(S)`，CSA 完整 latent 最多 1024 条。
- 溢出比例 `f` 用 128 卡合计存量对 `ROOM = 5.720 TB` 计算，然后乘到最忙卡的稀疏读上。

## 18. 两份场景稿

`docs/deepseek-96g-slo.pptx` 仍是 prefix 拉取 = 物理带宽 25%（12.5 GB/s）、Decode SWAP = H2D 51.2 GB/s。下面两份不改集群配置文件，只改这一处或两处带宽，其余公式不变。TP 仍是 8。生成命令：

```
python3 docs/build_deepseek_96g_slo_ppt.py cases
```

`docs/deepseek-96g-slo-uc1-kv100.pptx`：prefix 拉取改为物理带宽的 100%，每卡 50 GB/s，不叠乘 80%。Decode SWAP 仍是 51.2 GB/s。最后一页对照 25%。

`docs/deepseek-96g-slo-uc1-ttft-tps.pptx` 是这一档的单页对照。系统 Prefill TPS = 全局批 × 输入长度 / 该批实际 TTFT，按 128 卡一份副本、完整输入 token 计，不是只算 0.5% 现算 token。TTFT 展开为拉 KV、计算、AR、MoE。计算 = max(HBM, Attention FLOP)。最右列是相对同长度 25% 行的 TPS 提升，25% 行标为基线。

`docs/deepseek-96g-slo-uc2-swap400.pptx`：在用例 1 上，把 Decode KV SWAP 从 51.2 GB/s 改为 400 GB/s。输入长度收到 2M 和 4M，这里的 1M、2M、4M 是 1 048 576 的整数倍。最后一页同时对照 25% 拉 KV 和 51.2 GB/s 换入。
